# V4 radio2 CPU clock comparison, 9 November 2026 UTC

On this Heltec V4.3 OLED Full Companion build, 80 MHz added about 0.19 ms
per frequency-only switch and 0.24 ms when modem settings also changed,
compared with 240 MHz. The 12 measurement windows recorded 14,668 successful
switches with no new switch errors.

| CPU | Frequency only, mean | Frequency and modem, mean | Samples, frequency / modem |
| --- | ---: | ---: | ---: |
| 80 MHz | 1.052 ms | 1.236 ms | 2,268 / 2,148 |
| 160 MHz | 0.910 ms | 1.047 ms | 2,447 / 2,431 |
| 240 MHz | 0.864 ms | 0.995 ms | 2,656 / 2,718 |

The 80 MHz switching time was 22% longer for frequency-only changes and 24%
longer for mixed changes. These are instrumented means on this firmware and
configuration, not maximum latency guarantees, packet-loss results or battery
measurements. Timing instrumentation itself adds overhead.

## Power-saving policy

Auto now holds 80 MHz while radio2 or a temporary secondary profile is active
and device power saving is on. Turning power saving off selects the highest
supported Auto clock. Explicit clock choices still take precedence; the
Indicator retains its existing exception.

Physical checks passed for starting radio2 with PS on, live PS off/on toggles,
an explicit 160 MHz selection across both PS states, and returning to Auto.
Readback confirmed the actual clock at each step. The 34 focused clock,
profile, receive and USB-sleep tests passed; seven documentation checks passed.
Host tests cover Companion, Repeater, Room and Sensor roles, clock changes
before retuning, SDK PM bounds, stable scanning, and the Indicator exception.

## Method and firmware

Both receive profiles used 8 MHz SPI with all seven fast-switch features on.
The primary was 906.525 MHz, BW 62.5 kHz, SF7, CR5, preamble 32. The secondary
was 907.525 MHz with either the same modem settings, or BW 500 kHz, SF5, CR5,
preamble 200. No test packets were transmitted; ambient traffic was not
controlled.

For each pair, clocks ran in order 80, 160, 240, 240, 160, 80 MHz. Each window
had 20 seconds without CLI traffic, with PS on throughout to isolate the CPU
clock change. Clock application and its settling interval preceded the samples.
Means use independent count/sum deltas for both switch directions, weighted
by sample count. The timing recommendation cooldown did not block scanning.

Source was `7f521c1e007dead866327c0312dda82c114392f6` plus this Auto/PS fix,
target `heltec_v4_2_v4_3_companion_radio_full_femon`, Cascade profile.
The timing image enabled `MESH_HIL_ESP_SPI_AB`, `MESH_HIL_PROFILE_TIMING` and
eight histogram bins. Normal and timing builds passed capability, partition
size and runtime-RAM checks. Detailed measurements and image hashes are in
the [sanitized results](esp32_radio2_ps80_2026-11-09.safe.json).

The normal image was restored after measurement, with application verification,
fresh runtime identity/version checks and no timing commands remaining.
The original primary settings, radio2 off, PS off and Auto at 160 MHz were
restored. The new 80 MHz policy remains installed for subsequent PS-on use.
