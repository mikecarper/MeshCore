# T1000-E HEAD BLE validation — 2026-11-01
<p class="meshcore-hosted-doc-link"><a href="https://mikecarper.github.io/MeshCore/test-results/t1000_ble_head_2026-11-01/">View this page on MeshCore Docs</a>.</p>

**PASS:** the Mercerwood T1000-E completed three authenticated 30-second BLE
sessions with its USB cable physically unplugged, using the existing bond.
Each session returned the exact USB-bound public identity, device information
and full firmware version, with advancing uptime and zero core errors or queued
outbound packets. The controller trace contains exactly three successful
connections, three encryption successes and three requested disconnects. No
failed establishment, timeout or ATT `0x0e` occurred.

The installed Full Companion firmware is
`v1.18.0.2-halo-keymind-cascade-dev-8cc67955 (Build: 01-Nov-2026)` from
[`8cc67955a`](https://github.com/mikecarper/MeshCore/commit/8cc67955a127fa3de7d5c780254e31a5cb35067b).
`git pull --ff-only` found the branch already current. The application-only ZIP
passed capability, size, runtime-RAM budget and compiled DFU handoff checks before flashing.
Its SHA-256 is
`26414355de9f2596714de3ee0cd30323e4e79804f636ab364e975de8286897fa`.

The first updater attempt stopped before touching the device because its
unprivileged process-owner inspection could not inspect every process. The
previously reviewed read-only sudo owner-inspection path then completed DFU.
No erase, bootloader or SoftDevice update was requested. Fresh USB readback
verified identity, PIN/device preferences, contacts, channel names/keys and the
checked RF, Bluetooth, power and GPS policies. Twelve query cycles and three
USB reopens passed with zero core flags. The old sticky radio-watchdog flag
was recorded before the expected firmware-update reboot.

After the user physically unplugged USB, an initial 10-second BLE diagnostic
passed. The main qualification then authenticated through a protected read
before subscribing, sent sequential local Companion requests and held each of
three connections for 30 seconds. It omitted optional MTU acquisition and
accepted fragmented replies. Bleak's fallback MTU readback was not treated as
the negotiated link MTU.

| Main session | Initial uptime | Final uptime | Core flags | Controller result |
| --- | ---: | ---: | ---: | --- |
| 1 | 362 s | 392 s | 0 | Encrypted; requested disconnect `0x16` |
| 2 | 406 s | 436 s | 0 | Encrypted; requested disconnect `0x16` |
| 3 | 451 s | 481 s | 0 | Encrypted; requested disconnect `0x16` |

A separate 30-second battery-only comparison used the older client sequence:
MTU acquisition before notification subscription and application commands.
That also passed, with acquired MTU 247, one encrypted connection, one requested
disconnect, advancing uptime from 519 to 549 seconds and zero core flags.
This comparison did not reproduce the earlier ATT failure.

T1000-E firmware intentionally pauses BLE while enumerated by a USB data host.
Closing a serial terminal does not release that policy. The earlier software
USB-deauthorization trial on `cfc9d44b` produced no target advertisement; it was
not equivalent to this physical cable-unplug trial. Host WiFi, adapter settings
and bonds were left unchanged throughout the BLE checks. The device was left
on battery, disconnected from our client, with the monitor stopped.

The [October 28 failure](hardware_validation_mercerwood_1_18_0_2_2026-10-28.md)
remains historical evidence. This test establishes working BLE in the physical
unplug condition on HEAD; it does not assign the old failure's root cause or
identify a new firmware BLE fix. Fresh pairing, phone clients, a battery-only
cold reboot, sustained traffic and a long soak remain outside this check.

The [sanitized evidence](t1000_ble_head_2026-11-01.safe.json) includes installation,
session and controller summaries plus trace and harness hashes. Raw traces and
USB snapshots remain private because they can contain credentials.
