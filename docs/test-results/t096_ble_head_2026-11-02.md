# T096 HEAD BLE validation — 2 November 2026 UTC
<p class="meshcore-hosted-doc-link"><a href="https://mikecarper.github.io/MeshCore/test-results/t096_ble_head_2026-11-02/">View this page on MeshCore Docs</a>.</p>

**PASS:** the Mercerwood T096 completed three authenticated 30-second BLE
sessions on HEAD with USB enumerated and serial clients closed. Each session
matched the fresh USB identity, device information and full version. Core flags
and outbound queues were zero at both ends. The controller recorded exactly
three connections, three encryption successes and three requested disconnects,
with no `0x3e`, `0x08`, `0x22` or ATT `0x0e` failure.

The physical unit matched the expected public identity and model from the
October 28 private inventory. Its USB UID differs from the older tracked
inventory entry, so installation used a private inventory for the freshly
verified unit. No board override or shared-VID/PID selection was used.

The Full FEM-on application is
`v1.18.0.2-halo-keymind-cascade-dev-8cc67955 (Build: 02-Nov-2026)` from
[`8cc67955a`](https://github.com/mikecarper/MeshCore/commit/8cc67955a127fa3de7d5c780254e31a5cb35067b).
Its ZIP SHA-256 is
`4fb87768d303b396bcc6da16ab38c2c77dbb8e6362e2f7131ac6012c3b804ba4`.
Capability, size, runtime-RAM budget, compiled DFU handoff and application-only
package checks passed. Runtime RAM admission was 84,140 available bytes against
73,728 required. The image uses the T096 S140 v6 layout at `0x26000`.

The application-only installation preserved identity, PIN/device preferences,
contacts, channel names/keys and the checked RF, Bluetooth, GPS, power, regulator
and FEM policies. No erase, bootloader or SoftDevice update was requested.
Twelve USB query cycles and three reopens passed. The old sticky radio-watchdog
flag was recorded before the expected update reboot; the new image reported
zero core flags.

| Main session | Initial uptime | Final uptime | Core flags | Controller result |
| --- | ---: | ---: | ---: | --- |
| 1 | 90 s | 121 s | 0 | Encrypted; requested disconnect `0x16` |
| 2 | 135 s | 166 s | 0 | Encrypted; requested disconnect `0x16` |
| 3 | 179 s | 209 s | 0 | Encrypted; requested disconnect `0x16` |

The main client authenticated through a protected read, then subscribed and
sent sequential local APP_START, device, version and core-stat requests. It
accepted fragmented replies and omitted optional MTU acquisition. Bleak's
fallback MTU readback was not treated as the negotiated link MTU.

One additional 30-second comparison used the older sequence: MTU acquisition
before subscription and application commands. It also passed, with acquired
MTU 247, one encrypted connection, one requested disconnect, uptime 266 to 296
seconds and zero core flags.

The initial text classifier missed the third disconnect because `btmon` clipped
its event heading at the default output width once packet numbers reached four
digits. Re-decoding the **same original btsnoop** with `-i 0 -C 240` recovered all
three requested disconnects and produced a complete clean classification.
The original text and incomplete classifier result remain private. This was a
decoder correction, without another hardware trial. It does not invalidate the
[October 28 result](hardware_validation_mercerwood_1_18_0_2_2026-10-28.md), which
explicitly recorded four connections and an additional `0x3e` disconnect.
That historical cause remains unassigned.

A final USB snapshot verified preserved identity, device information, contacts,
channels and checked policies. At uptime 351 seconds, core flags and queue were
zero. FEM RX gain remained on, TX PA remained fixed on, and the regulator stayed
automatic with active DCDC and no recorded crashes. The one enumerated serial
interface was unowned, Bluetooth was enabled with its existing host bond,
the BLE client was disconnected and the monitor had stopped.

USB authorization, host WiFi and adapter settings were not changed during the
BLE tests. Unlike T1000-E, T096 has no USB-priority BLE inhibition. This check
used an existing bond and idle serial handles; it does not qualify fresh
pairing, phone clients, battery cold boot, simultaneous serial traffic, a long
soak, sustained load or RF/FEM performance. No firmware BLE fix is inferred.

The [sanitized evidence](t096_ble_head_2026-11-02.safe.json) records installation,
sessions, corrected controller classification, final readback and harness
hashes. Raw snapshots and traces remain private because they can contain
credentials.
