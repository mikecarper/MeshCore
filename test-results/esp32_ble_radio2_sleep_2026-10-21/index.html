    ESP32 Bluetooth shutdown and radio2 CPU idle, 2026-10-21

    The ESP32 changes cover two gaps identified while qualifying nRF52 CPU sleep: reversibly stopping the Bluetooth host/controller, and allowing bounded MCU light-sleep during a settled secondary-radio receive visit. This report separates host/build coverage, SDK wait measurements and physical packet tests.

    Bluetooth transitions and quiet-window SDK wait checks pass. Three strict RF trials with power saving on and matched preambles received five of six packets, including the trial after the IRQ fix. They remain failures; radio2 is not fully qualified.

    The first V3 CPU-clock sweep stopped during setup, before any of its 20-packet-per-frequency cases transmitted. Switching Bluetooth off exposed a NimBLE-Arduino 2.5.1 shutdown crash: PC zero in the host task, with the event address resolving to ble_hs_timer + 8. This matches upstream issue #1184 and its merged fix #1185. The backport removes premature timer deinitialization while leaving final cleanup intact. The earlier V4 Bluedroid checks do not qualify V3 NimBLE. The regression reproduces the original null callback, then passes 1,000 shutdown/cleanup cycles under ASan/UBSan for each timer backend. Library version, source hash and build-local middleware checks also pass.

    Full Companion source 6236eec3 includes that repair and a preferences-reader fix for a truncated timezone record colliding with the new CPU footer length. Both timezone and CPU suites pass; damaged CPU overrides still fall back to Auto. V3 and V4.3 OLED FEM-off builds pass all 24 capability markers and their memory gates, at 2,118,680 and 2,556,504 application bytes respectively.

    The V3 received one application-only update after its old application hash was verified. Complete new-image readback passed, with its partition table and OTA metadata unchanged. Starting with Bluetooth saved off, it restored Bluetooth on and completed three off/on cycles without a reboot or core error. Uptime advanced from 32 to 58 seconds across 20 health samples. Every Binary handoff revalidated board identity and source version. The final checked configuration and credential hashes matched the baseline, and the active PIN stayed unchanged. This physical check covers Bluetooth power transitions, USB control and checked preference preservation.

    The recovery also exposed an already-ROM ESP32-S3 UART finish gap. The flasher now explicitly releases the boot strap before its final reset; its regression passes with both esptool command spellings. That separate fix is published in meshfirmware f9d03d1.

    Behavior and safeguards

    Bluetooth off disconnects clients and completes host/controller teardown in the main loop. Bluetooth on rebuilds the service without releasing controller memory permanently or clearing successful bonds. Address, name, PIN and saved stealth policy remain intact. Pending or failed teardown prevents CPU sleep. The Bluedroid characteristics have deterministic TX/RX registration order; heap fragmentation must not change a paired client's cached handles. On SDKs using automatic Service Changed handling, a small asynchronous service change requests client rediscovery after authentication. A local SDK completion is not treated as proof that the client refreshed its cache. Only actual use of the current notification and receive handles permits skipping this request on a later connection from the same peer within that host session.

    Companion, Repeater, Room Server and Sensor can idle during an eligible radio2 visit. The decision requires a settled, validated receive profile, working radio GPIO wake, no pending reception and physically stopped wireless drivers. An absolute scanner deadline is checked again at sleep entry. The timer budget is at most 10 ms, reserves a 4 ms early-wake scheduling guard and requires at least 2 ms remaining. Calibration, repair, ownership, queue, network, USB and role deadlines retain their existing guards. The receiver stays on. This does not enable sleep through an active Bluetooth/WiFi link.

    Host tests and builds

    The scheduling, board wake, dispatcher and real role integration suites pass. Coverage includes expired and wrapping deadlines, stale profile proofs, pending interrupts, failed wake setup and SDK errors. The BLE adapter tests exercise actual production code with ASan/UBSan, ownership differences, partial initialization/teardown failures and repeated off/on cycles. Existing nRF52 event/profile tests also pass; nRF52 hardware was not touched.

    All 22 scripts in the affected Sensor/tracker/sleep CI step and all 57 in the Companion contact/channel step pass locally. The latter initially encountered a missing Python platformio module in one read-only metadata case; that script's six cases passed with the existing PlatformIO Python environment. No firmware build or hardware test was repeated for this environment correction. The diagnostic fixtures exercise the current production sleep branches rather than relying on obsolete source anchors.

    The initial sleep/teardown implementation, before the cache fix, has Full V4.3 FEM-off Companion, V3 Companion, V4 Repeater, Room and Sensor builds that pass their capability and memory gates. ESP32-C6 BLE (Arduino 3.1.3), the NimBLE-Arduino V4 trial and RC32 Full (Arduino 3.3.11) also compile. RC32 exposed SDK service ownership and array-deletion defects; a version/hash-bound build-local repair fixes those sources without editing a shared SDK install.

    The cache fix is published in 1087643ae. Its V4.3 FEM-off Full and RC32 Full builds pass all 24 capability markers and their application size gates: 2,551,592 and 2,152,840 bytes respectively, each within a 6,553,600-byte application slot. The other earlier builds do not constitute a full build matrix of this later source revision.

    d34e65175 removes unnecessary delays between successful cache-recovery phases while retaining bounded failure backoff. Its V4 Full build passes, at 2,551,608 bytes. The same-size V4 build of f8b5b8301 adds only the channel-response padding fix described below. Bluetooth, radio, sleep-policy and role code are unchanged between those last two revisions.

    Classic Heltec V2 BLE remains below its required 8,192-byte internal RAM reserve. Historical checks left 2,552 bytes free on the baseline and 1,224 bytes on the initial sleep candidate. Removing an unnecessary WiFi-driver reference recovered 1,208 bytes, raising the later candidate to 2,432: 120 below baseline and 5,760 short of the reserve. Final cache/padding revisions were not remeasured on V2. The gate was retained; this target remains unqualified.

    Physical V4 observations

    The test board is a Heltec V4.3 OLED using its matching FEM-off Full Companion image. The first candidate reports source suffix 278c9ffb; its published equivalent after history cleanup is 61eecbd97. An application-only write and complete readback preserved the partition table, OTA metadata, identity, settings and credential digests. No whole-flash backup, bootloader write or other-device update was performed.

    With Bluetooth/WiFi off and power saving on, only this V4's USB data was suspended. After the host-loss grace period, a 90-second diagnostic window recorded 4,635 SDK light-sleep calls and returns, zero SDK errors, zero short waits, zero vetoes and zero pending-wake returns. Cumulative call time was 35.523299 seconds; the longest call was 9,869 microseconds. The mixed profiles were 910.525 MHz / BW62.5 / SF7 / CR5 and 916 MHz / BW125 / SF9 / CR5. USB authorization and runtime policy were restored. Core errors remained zero. These are SDK wait measurements, not electrical current or residency readings.

    Two initial saved-bond Bluetooth off/on sessions passed. Further testing exposed both a host-side notification-acquisition problem and a real firmware GATT-handle ordering defect. The host driver now uses ordinary StartNotify. The original failures are retained; clearing a client cache is not accepted as proof that firmware handles remain stable or an existing cache migrates.

    On d34e65175, both authenticated NUS connections passed with the old opposite handle cache retained. The test independently checked board, exact version, role, public identity, node name, address and advertising policy. Switching off while connected disconnected the client; the test required completed off before re-enabling and reconnecting. No cache was cleared and no new pairing was made. The cache changed automatically to TX value 0x002A, RX value 0x002D; saved pairing-key digests were unchanged. The image also started successfully with Bluetooth saved off. No electrical power measurement was made.

    Two-frequency packet controls

    The peer is an independently identified ESP32 XIAO S3 WIO. Every transmitted packet uses a new encrypted nonce, full sender/destination identities and a zero-hop direct route. The receiver's USB data is absent during the sleeping RF window; queued packets are checked only after USB resumes. WiFi and Bluetooth are stopped, crossover is off, and physical RX counters must advance on both frequencies. No failed packet is resent automatically.

    Earlier runs used a transmitter preamble of 128 symbols while the receiver reported 32. An awake two-packet control received zero packets with zero SDK sleep calls. Disabling radio2 then received the one primary test packet. Source inspection found that the receiver's 32-symbol preamble guards expire after about 99/198 ms, while a 128-symbol transmitted preamble alone lasts 262/524 ms on these profiles. The guard can clear preamble detection and permit a scan hop before the header arrives. These mismatched trials remain recorded; they do not establish a CPU-sleep regression.

    GPIO wake and packet ownership

    ESP-IDF 4.4.7 documents that GPIO interrupts are not generated during light sleep. GPIO wake is a separate mechanism. The board temporarily uses a level wake source and then restores a rising-edge interrupt; the SDK's GPIO driver and S3 wake implementation do not replay a software callback when that interrupt type is restored.

    The wrapper previously checked only its software event. If a completed packet left DIO high without a callback, the loop could fail to claim its FIFO before a later rearm or retune. This is a concrete ownership gap, but the aggregate packet results do not prove which missing nonce encountered it.

    1ba4e2830 adds an ESP32-only physical IRQ fallback to both pending and claim checks. It uses that registered radio module's own pin and HAL, validates ownership, null pointers, NC, pin range and the SoC validity mask, and adds no RAM fields. Claiming consumes any software event too; the unchanged hardware RX_DONE check still gates FIFO reads. It changes no frequency, preamble, wake mask or sleep budget. Other platforms retain their software-event behavior.

    All 12 interrupt-recovery host tests pass with ASan/UBSan. They execute the production receive and reconfiguration paths with an asserted DIO and no ISR, combined and delayed callbacks, independent radio pins, invalid pins and non-ESP32 variants. Removing either fallback fails an executed regression assertion. The V4 Full build passes all 24 capability markers and its memory/size gates, at 2,551,736 bytes within the same 6,553,600-byte application slot. The RC32 Full build on Arduino 3.3.11 also passes all 24 markers and its memory/size gates at 2,152,968 bytes. These are build checks, not physical RC32 qualification.

    The application-only installation and full readback of this image passed, including unchanged partition table, OTA metadata, identity, saved settings and credential digests. One new six-packet qualification trial then exercised the changed IRQ code with the same radio settings, USB suspension and power-saving policy. It received 5/6, missing secondary sequence 6: another strict RF failure. All six sends completed once; none was resent. Profile RX deltas were 79/2, including ambient traffic, with five direct packets and two receive errors. The interval recorded 741 SDK calls/returns, zero SDK errors, short waits or pending returns, and two safe vetoes. Cumulative call time was 5.710857 seconds; the longest was 9,900 microseconds. Cleanup and PS-on restoration passed.

    Independent source audits found no additional concrete clock/deadline defect: ESP32 micros() and the scanner use the ESP Timer domain; the deadline is anchored before the late query and checked again after wake setup. Pending packets and latched preamble/header activity guard the next retune. The current 4.6-symbol scanning model is not a zero-loss guarantee. The observed losses remain unresolved; neither interference nor the IRQ gap is established as their cause. No further unchanged RF trial or arbitrary timing/preamble change was used to obtain a pass. Further qualification needs a control that holds CPU speed fixed and correlates scan/preamble/IRQ timing with individual packets.

    Channel cleanup and response padding

    The single-profile and sleeping reports also recorded cleanup failures. The single-profile power restore was refused while the radio was busy; a separate bounded cleanup restored 22 dBm and removed only the hash-matching test channel. The later sleeping run restored power and cleared its channel but failed a raw channel-response digest comparison.

    A separate read-only audit compared every meaningful channel name and every key byte twice on both devices. All matched, and both temporary slots were empty with zero keys. Raw differences occurred only after the terminating NUL in the fixed-width channel-name field: one channel differed between repeated reads on each device and all 40 differed between devices. The getter used strcpy without clearing the unused name bytes, exposing stale reply-buffer padding. The original failed receipts were retained; no channel data was rewritten to force a digest match.

    The shared Companion fix zero-pads and bounds that field while retaining key offset 34 and the existing 50/66-byte frame layouts. All nine affected host tests pass. The actual-handler regression covers empty, short, maximum and unterminated names, dirty output buffers, Meshtext on/off and 16/32-byte keys; the original implementation fails its negative control.

    A read-only hardware audit on 1ba4e2830 also passed: both devices' meaningful channel names and every key byte matched across two reads, both temporary slots were empty with zero keys, and every V4 name field had zero padding. The peer's firmware was not changed.

    V3 fixed-clock comparison with 20 packets per frequency

    After the NimBLE repair, the V3 completed all four predeclared cases on 6236eec3. Every case sent 20 unique packets per frequency once, with the same 32-symbol preambles, 2 dBm peer TX power and default 10/4/2 ms sleep dials. Power saving stayed on; CPU speed and the temporary manual sleep switch were controlled independently. RX power saving was saved off for these comparisons; the profile scanner itself uses continuous RX during each visit.

    80 MHz Off 18/20 17/20 0/0
    80 MHz On 20/20 19/20 270/270
    160 MHz On 18/20 14/20 18/18
    160 MHz Off 19/20 16/20 0/0

    All 160 transmissions reached TX_DONE, with no packet retries or duplicates. All four strict delivery checks failed. Settings, channels and credential hashes were restored; both radios finished with zero core error flags. Losses with manual sleep off show that sleep is not required for the observed failure. Ambient traffic differed between cases, and these samples do not establish a CPU-speed relationship or a packet-loss cause.

    The On rows do not yet prove sleep during packet traffic. The UART quiet control stopped the driver but left its Companion session logically connected. Incoming messages then queued push notifications to that stopped transport; the existing pending-output guard correctly prevented sleep. Whole-window SDK calls could have occurred before traffic began. The delivery counts remain valid, but sleep comparison qualification requires retiring that UART session and timing evidence inside the RF sequence. No pending-work guard is bypassed.

    UART session repair and timed V3 comparison

    The campaign continued on 2026-10-22 with 7d0709bf0. UART quiet now retires only that USB protocol session after draining the ACK, including its pending reply owners and USB Reader output. The offline inbox and other transports remain active. A successful UART restart restores a fresh silent session; failed restarts keep the interface parked and retry. The integration regression reproduces the original stuck notification, then retains and downloads 40 actual receive frames without weakening sleep guards.

    ESP32 diagnostics now retain sixteen 16-second SDK-entry buckets, with explicit outside-window, saturation and missing-clock indications. The collector stays within its 256-byte budget; nRF52 layout and behavior are unchanged. The physical comparison requires a positive bucket wholly after the first confirmed TX_DONE and before the last TX request, including host/device clock uncertainty. This establishes SDK entries during the packet sequence, not sleep through a particular packet or electrical residency.

    Both Full Companion builds passed 24 capability markers and their memory gates. V3 and V4 application sizes are 2,120,088 and 2,557,400 bytes. Application-only updates passed full readback, unchanged partition/OTA metadata and checked configuration/credential preservation on both boards. No Bluetooth lifecycle or earlier quiet-only test was repeated solely for documentation changes.

    V4's new comparison stopped during setup, before Bluetooth-off was sent and before any case or RF transmission. The failure remains recorded and requires bounded raw capture before diagnosis. Cleanup restored checked settings/channels and verified a fresh MQTT PUBACK increase. This failed setup does not supply new V4 packet-delivery evidence.

    Final handback and limits

    Both V3 and V4 now run 7d0709bf0. Its original radio, RX power-saving, Bluetooth, WiFi, MQTT, logging, diagnostics and USB-watchdog settings were restored and checked against the frozen baseline, including credential digests. Radio2 is off (automatic allowed), preserving its original automatic permission. Bluetooth is on. WiFi reconnected and MQTT resumed with a verified fresh broker PUBACK increase. The peer's original 22 dBm power and logical channel state were restored. No nRF52 board, hub power or other firmware was changed in this task.

    The Bluetooth hardware checks pass. SDK light-sleep calls are observed without SDK errors. Strict sleeping two-frequency packet qualification remains open, and Classic V2 still fails its existing RAM reserve gate. These results do not qualify every ESP32 board or the full thirteen-radio fleet, and do not measure electrical power savings. Unchanged Bluetooth and quiet-wait checks were not repeated for padding, version, documentation or fixture-only changes.
