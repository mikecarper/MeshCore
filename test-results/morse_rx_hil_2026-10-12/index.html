    Morse receive hardware checkpoint - 12 October 2026

    Status: incomplete hardware validation. The release default remains 25 WPM / 902.100 MHz and the public limit remains 60 WPM. Experimental 255-WPM builds are not a validated release limit.

    Implementation and host verification

    • Companion, repeater, room and sensor command paths support bounded receive sessions, a volatile 4096-character capture, paged reads and checked LoRa recovery. Receive duration is one second through five minutes.
    • Remote receive starts only after its acknowledgement has actually transmitted.
    • Fresh focused Morse run: 56/56 passed. Additional high-speed HIL OFF-debounce tests and decoder matrix: 3/3 passed, including 188 synthetic waveform cases.
    • Radio/role regression run: 390/390. RS232 overlap: 19/19. USB/BLE/logging: 222 test methods with no functional failures; eight optional DFU emulation subcases skipped because the host lacks Unicorn.
    • Build checks passed for the tested nRF52 companions/repeater, ESP32 room and sensor, and compact STM32 builds. Compact STM32 retains TX but excludes RX by default to respect its existing flash boundary.

    Hardware identities and isolation

    The Mercerwood Pi was reached at 100.78.195.38. Only identity-verified application DFU packages were written through the existing mcfirmware.sh path. No bootloader or SoftDevice was replaced, no services were stopped, and the Pi was not rebooted by this test.

    The RAK3401 service radio and MeshTower were left alone.

    Early tests put CW at 909.5 MHz and packet profiles elsewhere. This was corrected: the requested CW default is 902.100 MHz, separate from the LoRa lab control tuple 909.5 MHz / 500 kHz / SF5 / CR5. Results from the early layout are not proof of packet-spectrum isolation.

    set radio only saves Companion primary settings. The test runners now use set tempradio and poll the exact active tuple; saved or pending settings do not satisfy the check. The USB-only HIL recipes explicitly include the existing temporary-radio capability. Names and saved primary settings are not changed by the corrected runners.

    Observations, not a new maximum

    • With experimental warm-XOSC TX, 800-us PA ramp, RSSI window 2 and 1-ms polling, MeshPocket-to-RAK decoded the alphabet/digit, word-spacing and punctuation messages correctly in one 120-WPM sweep at 902.100 MHz.
    • Reverse-direction captures contained additional noise characters. At 200/240 WPM, there were real character errors in both directions. Strict comparison includes extra characters; matching only a substring is not accepted.
    • Keeping ordinary FSK packet preamble/sync/CRC did not establish a reliable faster limit. That experiment is not enabled in production.
    • A no-transmitter control can produce extra characters; the source of those RSSI excursions is not established. Noise, another carrier and a radio measurement artifact must not be conflated without further evidence.
    • Sample-gap diagnostics confirmed mostly 1/2-ms cadence after noncritical sensor, display and filesystem work was deferred during capture. The protection of voltage cutoffs, GPIO expiry, watchdogs, transport input and stop commands remains active.
    • Integer-millisecond timing maps 219-255 WPM to the same nominal five-ms dot. SPI/PA overhead further slows the envelope. USB-observed TX duration is not a precision measurement of physical on-air WPM.

    Remote acknowledgement and retained-capture evidence

    A 30-second LoRa-controlled test physically demonstrated:

    1. A six-minute request was rejected in 0.682 seconds.
    2. The valid request was acknowledged in 0.684 seconds before RX started.
    3. The timed receiver returned to LoRa after 30.889 seconds as observed by the host.
    4. All 34 retained characters read locally were returned byte-for-byte in the remote LoRa read.

    The decoded RF text was not equal to the transmitted message, so this run failed overall. It used the early shared CW/control frequency and is not a clean decoder validation. The full five-minute and multiple-page remote tests remain outstanding.

    Why hardware work stopped

    At approximately 22:43 Pacific the RAK USB connection disappeared during the zero-gate isolated-frequency sweep. It subsequently reported v1.17.1.10-halo-keymind-cascade-preview3-9ce2a076, with get morse unknown, instead of the just-verified Morse application. Another concurrent job had flashed the shared RAK. This is not evidence of a Morse firmware crash. The affected sweep is incomplete and must not be counted as a completed speed test. Hardware writes were stopped for user coordination.

Default/production behavior, capture size and low-speed timing are unchanged. Synthetic tests pass; physical results are still pending.

    Follow-up: 13 October 2026

    The original checkpoint above is historical. Its implementation and Reader / RS232 integration were subsequently pushed as 0be4c7488 and 396304822.

    • The receiver now keeps its timing estimate in Q5 rather than whole milliseconds, eliminating the rounding deadband without changing its 4168-byte production allocation. Letter/word split thresholds of 2.25/5.5 dot units tolerate ordinary +/-20% gap jitter; doubled letter spacing remains explicitly ambiguous, not a supported exact-decoding result.
    • A volatile, default-off HIL transmitter injects seeded phase jitter, gradual speed drift and modest extra spacing. Its exact pre-key duration check retains the 180-second ceiling. Shipping images contain neither the HIL configuration nor its command branch.
    • Fresh focused verification passed 108/108 tests. The real HIL scheduler and receiver passed 154 exact human-timing vectors through experimental 240 WPM; 84 additional supported synthetic vectors passed. These are software tests, not physical RF speed qualification.
    • The CI stability group passed 106/106. The bridge recovery fixture now includes the actual RS232 power/heartbeat helpers and verifies byte-exact retained short writes. Source/published documentation links passed 7/7 tests plus browser-script checks.
    • Compact STM32 USB Companion links at 228868/229376 flash bytes with unchanged commands and ITU character support. An exhaustive 256-byte comparison verifies the compact ASCII lookup against the original.
    • All four nRF52 HIL targets compiled. Fresh application-only DFU packages were installed on the identity-bound RAK4631, MeshPocket and T096 without changing their bootloaders or SoftDevices.
    • A five-minute remote receive session expired and restored LoRa. All 424 captured characters were returned exactly in four LoRa pages, but the decoded RF text did not match the nine transmitted messages: this is a transport/recovery pass and a decoding failure, not an overall pass.
    • Six-second no-intentional-TX controls at 902.1 and 903.1 MHz were empty on the RAK, but produced false characters on the MeshPocket. A subsequent 25-WPM alphabet/digit message decoded exactly from Pocket to RAK; the reverse direction had errors. One clean message does not establish a zero-error speed limit.

    RF investigation and repeated standard/uneven-timing speed qualification remain in progress. Default 25 WPM, public ceiling 60 WPM, radio bandwidth, and shipping RF filtering have not been changed. Packet control stays at 909.5 MHz / 500 kHz / SF5 / CR5; CW remains separate at 902.100 MHz by default. Raw results remain in out/morse-rx/ and the Pi run directory above.

    Controlled speed and human-timing follow-up

    These are conditional laboratory results, not a promise of error-free reception on every board or with automatic noise detection. CW stayed at 902.100 MHz, packet control at 909.5 MHz / 500 kHz / SF5 / CR5, and requested chip TX power at -9 dBm. The Pocket / RAK pair used a volatile HIL-only -80 dBm receive floor against strong received tones. Shipping images do not contain this receive-floor setting. Earlier automatic-threshold quiet controls produced false characters on the Pocket and T096; that remains a separate qualification limitation.

    The original 2.25 / 5.5-dot letter / word boundaries failed ordinary uneven timing even at 25 WPM. With seeded +/-20% phase jitter, gradual -10% duration drift, and no extra letter or word spacing, the first sweep passed only 2/6 messages at each of 25, 60 and 120 WPM. A short, fully retained RF trace decoded VW MN DOG as VW MNDOG in all six directions/rate combinations. All 20 expected marks remained present; the second word gap measured 246 / 246 ms at 25 WPM, 100 / 102 ms at 60, and 54 / 52 ms at 120. The old word thresholds were 264, 110 and 55 ms respectively.

    The receiver now uses the ordinary 2 / 5-dot gap midpoints, without changing mark classification, RX allocation, RF filtering or the public speed limit. The same tight human-timing profile (seed 6789), with two repetitions of all three mixed alphabet/digit, word and punctuation messages in both directions, then passed strictly:

    Requested WPM Pocket to RAK RAK to Pocket Total exact messages
    25 6/6 6/6 12/12
    60 6/6 6/6 12/12
    120 6/6 6/6 12/12

    Only leading/trailing capture whitespace is removed in the physical harness; extra internal spaces, noise characters, missing letters and ? fail the test. There were no cleanup errors. This establishes zero observed errors in those 36 messages under the stated laboratory conditions, not universal 100% reliability or a 120-WPM release qualification.

    The production-equivalent RF comparison uses cold-XOSC TX, 3400-us PA ramp, RSSI window 0, two-ms sampling and ordinary OFF debounce. Compile guards and actual PlatformIO/SCons flag tests prevent faster experimental settings or a different receiver clock from being mislabeled as shipping RF behavior. The lab maximum override and diagnostics still make these HIL applications, not release images.

    Requested WPM is not measured RF pace. Four strict 13-word PARIS trials per rate transmitted 643 dot units, omitting the unsent final seven-unit word gap:

    Requested WPM Host-observed duration PARIS-equivalent pace
    60 14.354-14.365 seconds 53.7 WPM
    120 7.937-7.940 seconds 97.2 WPM

    The pace includes CLI response and polling overhead; it is not an oscilloscope measurement of RF edges. It also does not substitute for varied-text testing.

    Latest focused verification passed 129/129 test methods. The actual HIL scheduler / decoder matrix has 175 exact results plus one explicitly unsupported 240-WPM / two-ms-sampling / 50%-extended-spacing case. The separate human envelope matrix has 84 exact results plus 14 explicitly unsupported doubled-character-spacing cases. Unsupported transcripts remain checked and visible; they are not normalized or counted as exact-decoding passes. Former-threshold negative controls reproduce the tight-gap failure. The production receiver remains 4168 bytes, and compact STM32 still links at 228868/229376 flash bytes with its unchanged feature boundary.

    Faster experimental RF comparison

    The corrected fast SX1262 HIL applications use warm-XOSC TX, an 800-us PA ramp, RSSI window 2, one-ms sampling and the experimental short OFF-confirmation minimum. These are not shipping RF settings. The same -80 dBm HIL receive floor and exact-message checks were used on the same Pocket / RAK pair.

    Requested WPM Standard timing, two repeats Tight human timing
    120 Previously all-pass; not repeated in this boundary sweep 6/6
    150 Not tested in this boundary sweep 5/6
    200 12/12 3/6
    255 10/12 Not tested in this boundary sweep

    The tight human profile is again +/-20% jitter, -10% duration drift, no added letter/word spacing and seed 6789. At 150, DOG became DKG in one direction. At 200, three messages had real body or punctuation errors. The shortest timing bucket therefore does not qualify as zero-error, and neither does the higher uneven-keying speed. Integer rounding maps requested 219-255 WPM to the same five-ms dot, so 255 is not 255 measured WPM.

    The fast steady-PARIS pace check gives:

    Requested WPM Host-observed duration PARIS-equivalent pace Exact PARIS messages
    120 6.868 seconds 112.3 WPM 2/2
    200 4.273-4.277 seconds 180.5 WPM 2/2
    255 3.669 seconds 210.3 WPM 1/2

    The failed 255 PARIS capture contained PANIS in place of one PARIS. These rates include the same host/CLI overhead as the production-equivalent pace measurement; pace is calculated only for the 643-unit PARIS payload, not by applying that reference count to the other test messages.

    The strongest observed all-pass points are therefore 200 requested WPM for machine timing on the fast HIL pair, and 120 requested WPM for the tested uneven timing. Their steady-PARIS references are approximately 181 and 112 WPM respectively. With production-equivalent RF timing, the tested uneven-timing reference is approximately 97 WPM. None of these conditional limits resolves the automatic-threshold quiet-control failure or qualifies another board/radio family. Shipping defaults remain unchanged.
