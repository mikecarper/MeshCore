    Browser LoRa updater (experimental)

    This prototype runs in the browser using a USB-connected Companion or Repeater as the source. Direct and multi-hop updates have not yet been qualified on hardware. Wi-Fi support is still under development. Keep this page open during the transfer; closing it disconnects the file source.

    Use Chrome or Edge on a computer with Web Serial support. To start, connect the Companion by USB and choose Connect USB source. Choose a contact, select the firmware, then choose Check firmware and target. After checking the result, choose Transfer, then Install and verify. The target needs a firmware build that supports verified ota installhash.

    1. Connect your radio

    Plug in your USB radio, then connect it and choose the device to update.

    Device to update

    Connect a Companion to load contacts.

    Enter a public key manually

    For a USB Repeater source, enter the target key here before connecting.

    2. Choose firmware

    Get firmware from GitHub releases

    To make a smaller differential update, also select the exact firmware currently installed on the target.

    3. Send and install

    Keep this page open during the transfer. Check the status below before installing.

    Advanced connection and firmware options

    Repeater forwarding

    Optionally change forwarding on the source or target. The radio flood settings leave direct-route messages enabled; all forwarding controls both. These saved settings need firmware that supports them. A relay used by the selected route must keep forwarding on. To manage a different repeater, connect with that repeater as the target first. Restore the setting afterward if needed.

    Multi-version nRF52 update

    For nRF52 internal staging, choose the exact installed firmware above, the final firmware above, and optionally up to six intermediate images below. Each intermediate must contain OTA receiver evidence; the actual node is checked after every reboot. Prepared packages are unsigned. Use the single-update controls above for ESP32 or nRF52 with external storage.

    For supported RAK3401 and RAK4631 internal-storage OTAFIX builds, the browser simulates every selected differential using the identified bootloader. The simulation does not replace testing intermediates on the actual hardware. Full-package intermediate steps are not yet modeled.

    Estimates exclude retries, status polls and congestion. Use the single-update controls for an actual update.

    Setup and advanced details
    

    The source needs a Full Companion build with guarded direct OTA support, or
a Repeater with ota.peer and USB folder support. Older Companion builds
without the guarded USB capability cannot be used as a source. The target needs firmware
that supports the verified ota installhash command;
older versions cannot install through this updater yet. Before starting, put both radios on matching
active TempRadio settings matching their saved primary channel, set RX power saving off, and turn
automatic OTA fetch and install off. For a direct update, set OTA hops to 0.
Existing downloads and source folders must be cleared first. If the source
clock is wrong, set it before connecting. Multi-version updates require a
supported identified RAK bootloader and successful simulation of every step.
    

    For multi-hop, enter each relay's full public key in order from the source to
the destination. The source must already have ACL access to every relay and
the destination. This selects the administrative route; the firmware still
floods OTA data and does not restrict bulk traffic to these relays. Every participant must use the same saved and temporary
radio settings, with radio2 and crossing off; relays must have repeat on. Set
OTA hops high enough for the route on every participant. These checks are
experimental and have not yet been verified over LoRa.
    

    Alternatively, connect with the admin-route field empty, enter the full keys
of candidate repeaters, and select Find admin route. The search checks
cached neighbor reports from reachable ACL-authorized nodes. It favors fewer
relays among paths meeting the selected SNR floor, then the strongest weakest
link. Reports can be stale and do not identify which radio profile heard them.
This is a hint for the admin route; it does not select the OTA data flood path.
    

    Choose a firmware .bin or Nordic DFU .zip to create a full package in the browser, or a
prebuilt .mota package. Differential packages also require the exact new
firmware .bin; the target's existing firmware must match the package's base
hash. A signed package requires its full trusted signing key, which must also
already be trusted by the target. The target makes the final full-key check.
    

    To create a differential package in the browser, select the new
.bin and the exact old .bin currently installed on the target. The browser
reconstructs the generated patch and checks it against the new image; the target
also checks it during installation. nRF52 generation requires a supported
embedded layout and confirmed internal or QSPI staging; unsupported nRF52 layouts
can use a compatible prebuilt .mota.
Preparing a differential for a large image can use substantial browser memory;
if preparation fails, remove the old image to use a full package instead.
